  batch_window_ms: 50

  - id: "gpt-5-nano"  cost_in: 0.05  cost_out: 0.40  tier: "easy"
  - id: "gpt-5-mini"  cost_in: 0.25  cost_out: 2.00  tier: "med"
  - id: "gpt-5"       cost_in: 2.50  cost_out: 10.00 tier: "hard"

cache:
  exact:       enabled: true  backend: "redis"           ttl: 86400
  semantic:    enabled: true  backend: "qdrant"  sim: 0.95  ttl: 3600
  episodic:    enabled: true  backend: "redis+sessionid"  ttl: 300

rules:                                                  # evaluated top-to-bottom, first match wins
  - when: "cache.exact.match == true"             route: "cache.hit"
  - when: "cache.semantic.sim >= 0.95"          route: "cache.hit"
  - when: "step.type == 'verify' and tokens < 200"  route: "gpt-5-nano"
  - when: "difficulty <= 0.35"                     route: "gpt-5-nano"
  - when: "difficulty <= 0.70"                     route: "gpt-5-mini"
  - when: "step.type == 'plan'"                     route: "gpt-5-mini"   # plan always verified by a second pass
  - when: "difficulty > 0.70 or self_eval.confidence < 0.6"  route: "gpt-5"
  - fallback: true                                route: "gpt-5-mini"

fallback:
  strikes: 3                                       # 3 low-confidence responses in a row → escalate one tier
  on_regression:  "rollback_to_previous_pareto_point"
  on_cache_poison: "purge+alert"

5 · Deliverable 3 — Sample routing policy explainedwhy 22% / why not 5%

Why 71% of calls go to nano

The difficulty estimator (calibrated logistic regression over 12 features: prompt length, JSON structure, prior-step success, domain tag, has-code, has-citations, has-uncertainty-phrase, plan/act/verify tag, conversation depth, tool-failure history, retry count, time-of-day) lands easy / med / hard at 71% / 24% / 5%. The 71% is mostly verify steps, short lookups, structured JSON extraction, and tool-call arg construction — exactly what nano is good at. Quality floor is enforced by the 5% Prometheus sample: if a 5% slice drops below 0.80, the router is rolled back one Pareto point automatically.

Why not push nano to 90%? At ~85% nano share, success drops to 0.74 — below the floor. The frontier of the curve is around 71% nano, 24% mini, 5% frontier. This is the knee of the Pareto.

Plan / act / verify semantics

The router is step-type aware. plan steps are never routed to nano (plan failures cascade). verify steps always go to nano first; if the verification is "high-stakes" (involves money, email send, db write), it escalates to mini. act steps use the difficulty estimator alone. The agent runtime emits a step_type field on every call; the policy reads it via rule 3 above.

This is the bit most routers miss. Treating all steps the same is why FrugalGPT underperforms on agent workloads — it sees tokens, not semantics.

6 · Deliverable 4 — Caching strategy3 layers, one purpose each

LayerWhat it cachesKeyTTLHit rateRiskMitigation
Exact raw prompt → response bytes sha256(prompt + model_id + system + tools_hash) 24h ~12% stale world-state (e.g. user said "today" and the cache hit from yesterday) include date_window in key · max 24h TTL
Semantic nearest-neighbor prompt → response qdrant.search(emb, top_k=1, sim≥0.95) 1h ~26% semantic-equivalent prompts with different correct answers (date math, prices) calibration set + reject-on-sensitive-tag (date, price, email, weather)
Episodic mid-conversation repeated tool calls session_id + tool + args_hash 5 min ~6% user changes intent mid-session explicit cache.purge(session_id) on user correction; never cache tool results, only model outputs
Total — — — ~38% — 5% Prometheus sample on all hits to detect poisoning

Cache hit decision code (Python, 18 lines)

async def cache_lookup(prompt, ctx, session_id, step_type):
    # 1. exact
    exact_key = sha256(json.dumps({"p":prompt, "m":ctx.model, "s":ctx.system}, sort_keys=True))
    hit = await redis.get(exact_key)
    if hit: return CacheHit("exact", hit)

    # 2. semantic — reject sensitive tags
    if any(tag in prompt.lower() for tag in ["today", "now", "price", "weather"]): return None
    emb = embed(prompt)
    near = await qdrant.search(emb, top_k=1, score_threshold=0.95)
    if near: return CacheHit("semantic", near[0].payload["response"])

    # 3. episodic (only for tool-call re-attempts)
    if step_type == "act":
        e_key = sha256(f"{session_id}:{ctx.last_tool}:{ctx.last_args}")
        hit = await redis.get(e_key, ex=300)
        if hit: return CacheHit("episodic", hit)

    return None

7 · Deliverable 5 — 30-day ship plan$0.45/task ceiling · 0.81 quality floor

Day 1 – 3 · Foundation

Stand up LiteLLM proxy + LangSmith traces

Mirror all production traffic. Baseline: measure current $/task and current success on a frozen 200-task golden set. Exit: dashboard shows live per-step cost with no behaviour change.

Day 4 – 7 · Cache

Deploy GPTCache (semantic, sim ≥ 0.95)

Back-end = Qdrant, embeddings = all-MiniLM-L6-v2 (free, local). Start with exact-only for safety. Exit: cache hit-rate ≥ 25% with zero quality regression on golden-200.

Day 8 – 12 · Difficulty estimator

Train difficulty_logreg_v1 on 5k labelled steps

Labels come from Prometheus-Eval on 5% sample. Features from the §3 list. Exit: estimator AUC ≥ 0.78 on hold-out; easy/med/hard distribution matches §5.

Day 13 – 17 · 2-tier split

Route easy → nano, hard → mini, frontier off

No frontier model in the pool yet — that's the safety net. Exit: success ≥ 0.78 on golden-200, $/task ≤ $0.65, no P95 latency regression.

Day 18 – 21 · 3-tier router

Add gpt-5 as the "hard" tier, add Prometheus-Eval as safety

The 5% sample judge is your regression alarm. Wire the rollback to the previous Pareto point. Exit: success ≥ 0.81, $/task ≤ $0.45.

Day 22 – 25 · Batcher + speculative

Queue 50ms window · speculative draft = nano, verify = mini

Exit: throughput +18%, no quality regression, $/task ≤ $0.32.

Day 26 – 28 · Hardening

Cache-poisoning guards · budget alarms · Grafana · Slack on-call

Reject sensitive-tag lookups. Add purge(session_id) on user corrections. Page on-call if $/task > $0.45 for 10 minutes.

Day 29 – 30 · Ship

Promote to 100% traffic · public Pareto curve

Lock the policy at v3. Pin a frozen generalization set of 50 tasks never used in training. Quarterly review. Final: $0.32/task, success 0.80, 38% cache hit, 5% frontier share.

9 · Verdictwhat to ship, in order

Ship the cache before the router. I keep watching teams spend three weeks on a fancy ML router and never turn on a 100-line semantic cache. The cache alone buys you 38% of the win. Then the difficulty estimator (a logreg, not an LLM judge). Then the 2-tier split. Then add the frontier tier. Then batching and speculative. Five phases, not one. If you ship the whole thing in week one, the regression alarm will fire and you'll spend week two debugging instead of week two saving money. Pace it.
